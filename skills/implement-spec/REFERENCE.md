# Implement Spec — execution contract

## Resolve before changing anything

Use `docs/agents/issue-tracker.md` to identify the configured GitHub repository, host and access method; verify the spec and every issue belong to the intended repository. For GitHub Enterprise, use the matching authenticated `gh` host (e.g. `GH_HOST=host gh issue view N --repo host/owner/repo --json title,body,state,url`); verify the host and command support through installed `gh` help. Do not assume `gh issue view` accepts a `--hostname` flag. Read **full bodies**, not just titles or labels, and follow spec issue links and `Blocked by` references until the finite approved set is explicit. Confirm the issue set with the user if links are ambiguous. `to-issues` produces `## Type`, `## Acceptance criteria`, and `## Blocked by`; these persisted fields, not automation-ready labels, control execution. Read repo `AGENTS.md`, glossary, ADRs, check configuration, and spec context. Do not execute Jira/other-tracker work: report that the GitHub-only `goal` dependency cannot handle it and ask for a supported path.

Build a table: issue URL/ID, Type, AC, blocker IDs, checkpoint, public-interface test plan, current graph state, and evidence. Block affected issues on missing or ambiguous Type/AC, cycles, unknown referenced blockers, and references to blockers outside the graph whose closure **and relevant integration** cannot be verified. Closed on GitHub alone is not proof of integration. Ask for clarification or evidence; never silently drop edges or treat parent/spec issue as a completed blocker. If an outside blocker is verified, record the commit/ref and checks establishing it is in the pinned base. Confirm that no issue already implemented on the base is scheduled twice. Ask questions one at a time where clarification is needed.

Graph states: **blocked** (dependency, approval or checkpoint missing), **ready** (all blockers verified, approvals present), **in-progress** (isolated work), **implemented** (worker claims AC evidenced and checks pass, commit exists; not integrated), **integrated** (parent integrated the commit, post-integration checks pass), **verified** (AC evidence and required human checkpoints confirmed on Spec branch). A dependency is satisfied only when its blocker is **verified**: integrated, checks green, AC evidenced, and required human/manual checkpoints confirmed. A pending HITL checkpoint blocks dependents; a child reporting done never releases them. Subjective/manual AC remain pending until human confirmation; an issue needing that confirmation cannot become verified autonomously.

## Approval contract

Present: spec and issue identities, graph/frontier and outside-blocker evidence; the exact Integration branch or other user-selected base ref **and pinned SHA**; `spec/<slug>` target and collision policy; worktree backend, unique directories, worker branch naming, check commands and evidence expectations; AC and check expectations for every issue, and interface/behavior test plans for the next dispatch (including seams between concurrent issues); defer detailed sequential plans until blockers are verified and `goal` conducts its per-issue gate; Type/HITL checkpoint timing; concurrency limit (default 1); commit ownership (parent in sequential mode, worker in parallel mode only if approved), whether parent may integrate, and permitted integration strategy (fast-forward or, when needed, a non-destructive merge commit); whether AFK integration may be batched; and failure/stop budget. Get explicit human approval **before branch creation or any dispatch**. Do not treat approval of `to-issues` breakdown as approval of implementation or a HITL checkpoint. On changed scope, base, check definitions, test plan, or merge policy, pause for renewed approval.

Use a private, agreed untracked scratch/temp path for a progress ledger (no credentials or secrets): base SHA, plan approval, refs/commit IDs, graph states, test/check outputs or pointers, checkpoints, failures, integrations and review findings. On resume, validate approvals against current plan and re-read actual issue bodies, branch HEADs, ancestry, worktree status, and checks; do not trust ledger state as ground truth. An existing `spec/<slug>` or worktree may be resumed with explicit human approval only after verifying the pinned base is an ancestor of its HEAD, the worktree is clean, and ledger claims match actual commits, issue state, and current approvals. Reconcile discrepancies with the user first; unknown or unrelated branches are collisions, not resumable runs. Never reset or overwrite silently. Keep active worktrees for recovery unless explicit cleanup is separately approved.

## Issue execution

Create the approved Spec branch from the exact pinned base commit in its own worktree; do not modify the shared Integration branch. Respect the repo's `wt`/worktrunk convention if present; pin the base rather than selecting a moving latest integration branch. Choose **one** worktree owner/backend in the plan. Prefer the repo's `wt` convention only after installed help confirms it can create from the pinned commit; verify the created HEAD equals that SHA. If unsupported or absent, propose native `git worktree add -b <branch> <path> <SHA>` and obtain approval before using it. Host-managed isolated worktrees require supported tools and explicit approval. Verify every new worktree HEAD equals its recorded start SHA. Do not mix ownership or use destructive reset to coerce a mismatched base. Name distinct per-issue branches/worktrees and confirm they start from a committed Spec branch HEAD. Start a new ready issue from the **current committed** Spec branch HEAD (record the exact SHA); do not launch on an uncommitted or failed integration.

Before implementation in each working checkout, follow `goal/REFERENCE.md`'s implementation preflight: verify required dependencies and run the approved focused baseline. Missing tools or unavailable required verification leave the issue **blocked**, not implemented or verified. A parent's installed dependencies do not establish readiness in a separate worker worktree.

Sequential default: explicitly load `goal/SKILL.md` and its reference, and `tdd/SKILL.md` plus needed references via the harness skill loader or by reading their files. Follow `goal`'s upfront human approval for the issue's TDD/public-interface plan and definition of green, even if a high-level spec plan was approved; its end is a human handback, not PR submission. Pass `goal` the already-resolved canonical issue URL, configured host/repository, full AC text, and evidence provenance; explicitly use its tracked-issue resolution path instead of inferring a different issue from branch/remotes. Fetch with the approved host/repo and compare the returned URL before implementation. Use the approved `gh-<number>-<slug>` branch naming. If identity or AC cannot be confirmed, stop; never let the inline-goal fallback silently replace tracked AC. Multiple/fork remotes are not authority for changing the approved repository. Ask for the per-issue approval before implementing and require its handback before integration. In this enclosing workflow, replace `goal`'s suggestion to run `submit-draft-pr` with the Spec coordinator handback; do not invoke PR submission. After accepted handback, the parent commits in the issue worktree only if the plan permits it, stages only reviewed in-scope changes, and records the resulting SHA; otherwise ask for commit permission and leave integration blocked. Tests exercise public interfaces; mock only system boundaries; one RED→GREEN slice at a time; never refactor while RED. Do not claim subjective AC verified by a passing unit test alone.

Optional parallel mode is **opt-in only**: approve a bounded concurrency count, disjoint issue frontier, anticipated shared-file/interface seams, unique isolated worktrees, branch bases and human-approved TDD plans for **every** dispatched issue in the parent before launch. When `goal` cannot conduct its own interactive approval in a background worker, the parent explicitly loads `tdd`, follows its planning/approval step for each issue, and dispatches a leaf implementer that follows the approved plan and loaded `tdd` instructions; no child spawns further children. Preserve the equivalent `goal` evidence, guard and handback contract, including human review before integration. If the agent host has no safe isolated worker/worktree capability, use sequential mode instead. Check authenticated available model IDs and supported thinking levels **before** dispatch; set an explicit supported thinking level (non-reasoning models require `off`). No hidden provider/model retry or substitution after failure: report and ask. Follow host supervision for async completion; do not spin/poll on a hung worker indefinitely. Stop/report on failures; preserve cancelled worktrees for recovery.

Tie verification to the tested revision and dirty state, recording exact commands and results. Distinguish setup failures and preliminary candidate passes from behavioral RED and final GREEN as defined in `tdd/SKILL.md`. For built/browser artifacts, rebuild from the final source before claiming GREEN; assert the intended observable behavior, not merely artifact generation or page loading. Later contradictory evidence invalidates the earlier completion claim until reconciled.

Worker deliverable: issue ID, start SHA, branch/head commit SHA (if commits were approved), clean status, changed paths, public-interface AC evidence, exact executed checks/results, manual/HITL items, and unresolved risks. No PR, push, issue closure, merges into Spec/Integration branch, destructive reset, or cleanup from a worker. Commit only with explicit plan permission; without an approved commit, leave issue implemented-but-unintegratable and ask how to proceed. Default checkpoint: parent obtains human approval of each worker handback before integrating. For HITL issues require the stated human checkpoint **before dispatch and again before merge**; don't equate a plan approval with the checkpoint. Optional batch integration without per-AFK handback requires separate explicit plan approval and valid clean evidence/checks for each issue; never waive HITL checkpoints.

## Parent-only integration and release of dependencies

Serialize integrations. Before each merge, verify issue branch start SHA and current head, clean worker and Spec worktrees, approved scope, commit ancestry, AC evidence, checkpoints, and checks against the current Spec branch. Prefer fast-forward when the worker started from the **exact current Spec HEAD** and contains that HEAD. If Spec HEAD advanced (e.g. parallel leaves), **do not** force FF, reset, or blindly replay: use the plan-approved non-destructive integration strategy (such as a merge commit), inspect overlap and dependencies, integrate one branch, and run all relevant checks against the result. If the plan did not authorize that strategy, ask first; conflicts or unexpected paths always require a new checkpoint. For collisions, conflicts, unexpected paths, stale checks, or uncertain AC, stop for human resolution; never use an auto-resolver as the default. If parent cannot safely integrate with permitted tools/branch policy, pause and request human action.

After each integration, record resulting Spec HEAD, rerun relevant checks and inspect AC on the integrated branch. If the same check fails three times in a row, stop; also stop on changed requirements, ambiguous blockers, hung worker, failed checks, or exhaustion of approved work budget. Do not release dependent issues until all blockers have passed integration checks and their required human/manual checkpoints are confirmed (verified state). If integration is not approved or evidence is missing, leave dependents blocked. Never rewrite the pinned base or shared Integration branch.

## Final gate

After all issues reach verified, run whole-branch check commands and compare `base SHA...Spec HEAD` to spec and every AC. Explicitly load `code-review/SKILL.md` and its referenced standards baseline; review the complete diff in independent Correctness, Standards and Spec passes against the pinned base and original spec/issues. For valid findings, define a fix-up item with finding references, AC, scope, and a public-interface test/check plan for approval. Execute it in a new isolated branch/worktree from current Spec HEAD, following the same sequential TDD gate, commit permissions, parent integration, checks, and re-review rules; do not make ad-hoc edits directly on the Spec branch. Preserve earlier regression coverage during fix-ups. If a test is replaced, explain which original behavior remains covered and why the replacement is equivalent or stronger; rerun both the retained behavioral coverage and the new focused regression. Documentation-only fixes use approved direct verification rather than invented tests. Stop and ask if a fix changes the approved scope. Report remaining findings distinctly by axis; do not collapse review into a single pass/fail. Hand the Spec branch and manual review checklist to the user. Opening/readying a PR, closing issues, pushing, merging to shared Integration branch, or cleaning worktrees are **separate**, explicit user actions, not the exit step of this skill.
